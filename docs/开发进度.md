# 阅痕 ReadTrace 开发进度

## 当前阶段

当前阶段：v1.0.8「数据主权发版后高危缺陷修复」（hotfix 0904 之后，未升版）

> 版本号自 v1.0.0 起启用正式序列：**1.0.x 顺延，走到 1.0.30 后升 1.1**。

v1.0.8（versionCode 44，2026-09-04）里程碑成果：
- **全量存档合并包 (Sovereign Backup)**：219 部作品连同角色谱 / 语录 / 章节大纲合成一个 JSON，「一个账号 = 一个 JSON」一次导入全部恢复，全程幂等不覆盖已有内容；
- **富内容 JSON 应用内本地导入**：缺失作品按条目媒介标记 / 文件名自动建库，一次导入即作品 + 富内容；
- **清空账号数据**：打字验证「我确定删除账号数据」二次确认，物理清空全部作品与关联维度；
- **黑胶全局播放与网易云歌单**：播放中返回不销毁页面、主页悬浮「正在播放」胶囊随时跳回、歌单多选导入与播放队列；0904 热修包（versionCode 仍 44）一并携带「按 sourceId 直取链修复永久缓冲」。

2026-09-05 高危缺陷修复（本轮已提交推送，尚未升版发版）：
- **数据库升版不再全量重置评分**（数据破坏级）：`runPresetSeedsOnce` 的「统一 8.0 基准」限定首次播种（此时库中无用户数据），升版重播种只补种新增预置条目；种子插入评分兜底由 5 星制 5.0 改为十分制 8.0；
- **缓冲中拖动进度条必崩**：`onStartTrackingTouch/onStopTrackingTouch` 补 `isPreparing` 与空实例门禁，消除 Preparing 态 pause/seekTo 非法状态调用；释放播放器时同步清零总时长与拖动前播放标记；
- **唱机存活时点新作品被静默忽略**：`singleTask` 复用实例补 `onNewIntent` 接住新 `EXTRA_BOOK_ID`，切换时退出云队列接管并保持当前播放态；主页悬浮胶囊的跳回空 intent 不受影响。

### A 组 播放出错 code -38/0（P0）

**现象**

云歌单播放时 Toast 弹「播放出错 (code -38/0)」，播放胶囊键永久停在「缓冲中」，进度条 00:00 / 00:00 不动，无法重试，只能退出页面。

**根因**

1. `app/src/main/java/com/example/readtrace/VinylCassettePlayerActivity.kt:794-804` `releaseMediaPlayer()` 内用了 `runCatching { stop() }`。MediaPlayer 状态机中 `stop()` 仅在 Prepared/Started/Paused/Stopped/PlaybackCompleted 合法；而 `playCloudTrack():570` 与 `playAudioAt():713` 都在新播放启动前先调它，此时上一实例常仍在 `prepareAsync()` 进行中（Preparing 态），触发 native -38（MEDIA_ERROR_INVALID_STATE），extra=0。`runCatching` 只能捕获 JVM 异常，MediaPlayer 错误走 OnErrorListener 异步回调，捕获不到。这是 -38 的直接产生点。
2. `releaseMediaPlayer()` 未先解绑回调。旧实例的 onError / onPrepared / onCompletion 仍指向当前 Activity，导致「新曲正在缓冲，却弹出播放出错」的张冠李戴现象。
3. `VinylCassettePlayerActivity.kt:617-620` `playCloudUrl()` 的 onError 只弹 Toast 后返回 true，零恢复：不复位 `isPlaying`、不调 `setPlayingUi(false)`、不复位按钮文案、不释放 MediaPlayer、不重试取链，UI 直接死锁。对比 `playAudioAt():748-757` 是有删库重取逻辑的，云歌单路径漏了。
4. `VinylCassettePlayerActivity.kt:596` 用无 header 的 `setDataSource(url)`。而 `NeteasePreviewHelper.httpGet` 取链时带了 Referer 与 MUSIC_U；网易云 CDN 直链常校验 Referer/UA，裸请求可能被 403/302 拒导致 prepare 失败。
5. `VinylCassettePlayerActivity.kt:623` 与 `:762-765` 在 `prepareAsync()` 后无条件把 `isPlaying` 置真，prepare 失败后状态仍为真，`togglePlayState():407-429` 的分支判断随之走偏。
6. 无 `setOnInfoListener`（BUFFERING_START/END）、无 `setOnBufferingUpdateListener`、无取链与 prepare 超时兜底，弱网下永久「缓冲中」，用户无从区分卡住与失败。

**涉及文件**

- `app/src/main/java/com/example/readtrace/VinylCassettePlayerActivity.kt`

**修复方案**

- `releaseMediaPlayer()` 改为先 `setOnErrorListener(null)` / `setOnPreparedListener(null)` / `setOnCompletionListener(null)` 解绑，再用 `reset()` 替代 `stop()`（`reset()` 在任意状态合法，不会触发 -38），最后 `release()`。
- 新增 `isPreparing` 标志位，`prepareAsync()` 前置真、onPrepared/onError 置假，释放时据此跳过非法状态调用。
- `playCloudUrl` 的 onError 补齐恢复：复位 `isPlaying = false`、调 `setPlayingUi(false)`、按钮文案回「开始放唱」、调 `releaseMediaPlayer()`，并对同一次播放允许一次自动重新取链重试（`fetchTrackStreamUrl` 现取现用，直链不会过期）。
- 云直链播放改用 `setDataSource(context, Uri.parse(url), headers)` 三参重载，headers 传 Referer 与 User-Agent；MUSIC_U 仍只走应用私有 SharedPreferences，不落日志、不入 Git、不进任何 UI 文案。
- `isPlaying = true` 从 `prepareAsync()` 之后移到 onPrepared 回调内 `mp.start()` 之前。
- 补 `setOnInfoListener` 处理缓冲起止并更新按钮文案为「缓冲中 N%」，加 15 秒 prepare 超时兜底，超时按失败走恢复分支。

**验证方式**

模拟器上绑定 Cookie 后进入云歌单连播，反复快速点上一曲/下一曲 20 次，确认无 -38 Toast；断网播放确认按钮复位为「开始放唱」且可重试；`./gradlew assembleDebug` 编译通过。

### B 组 部分显示被遮挡（P0）

**现象**

唱机页底部「我的歌单」「去网易云搜索」两个 chip 只剩上半截被屏幕底边裁切；顶栏右侧 chip 被挤出屏幕只剩残字；档案页艺术头像第 5 个起被右边界切断。

**根因**

1. `app/src/main/java/com/example/readtrace/VinylCassettePlayerActivity.kt:141-147` insets 回调写的是 `systemBars.bottom + view.paddingBottom`，即每次分发都在上一次结果上再加一遍，paddingBottom 单调增长（XML 初始 24dp → 72dp → 120dp ...），底部控制卡片被逐步顶出屏幕。insets 回调确实会被多次触发（重新 attach、配置变化、requestApplyInsets）。这是底部按钮被裁的直接根因。
2. `app/src/main/res/layout/activity_vinyl_cassette_player.xml:29` 顶栏写死 `paddingStart="60dp"`（为 `FloatingBack` 悬浮返回键让位），叠加 root 的 `systemBars.left`；顶栏标题 16sp bold 带 emoji，右侧两个 chip 各约 70dp，窄屏下总宽溢出，右侧 chip 被推出屏幕。
3. `app/src/main/res/layout/activity_curator_profile_edit.xml:115-127` 与 `app/src/main/res/layout/activity_curator_auth.xml:273-285` 的 HorizontalScrollView 同时设了 `scrollbars="none"` 与 `overScrollMode="never"`，12 个预设头像只露前 4 个，且没有任何可横滑的视觉暗示。
4. `app/src/main/res/layout/activity_vinyl_cassette_player.xml:20` 写死的 `paddingTop="12dp"` 被 insets 回调用 `systemBars.top` 直接覆盖而非相加，设计间距丢失。与既有坑「顶栏写死 paddingTop 与 centerInParent 组合导致标题被 clipToPadding 裁顶」同源。

**涉及文件**

- `app/src/main/java/com/example/readtrace/VinylCassettePlayerActivity.kt`
- `app/src/main/res/layout/activity_vinyl_cassette_player.xml`
- `app/src/main/res/layout/activity_curator_profile_edit.xml`
- `app/src/main/res/layout/activity_curator_auth.xml`

**修复方案**

- insets 回调改为幂等写法：以 XML 中记录的初始 padding 为基准常量（用 `view.getTag()` 存初始值或提为字段），每次回调都用「初始值 + 当前 insets」重新计算，不做累加；paddingTop 同样改为 `initialTop + systemBars.top`。
- 顶栏 `paddingStart` 由 60dp 降到与悬浮返回键实际占位匹配的值，并给标题 TextView 加 `ellipsize="end"` + `maxLines="1"` + `layout_width="0dp"` + `layout_weight="1"`，让标题让位而非把右侧 chip 挤出去；两个 chip 保持 `wrap_content` 不参与压缩。
- 艺术头像 HorizontalScrollView 打开 `scrollbars="horizontal"`，或在列表末尾追加一个「更多 →」渐隐提示项；同时给容器加 `fadeScrollbars="false"` 保证首次进入即可见滚动条。

**验证方式**

唱机页反复切后台再回前台 5 次，确认底部两个 chip 始终完整可见、位置不漂移；旋转屏幕一次后复核；顶栏在窄屏（360dp）下确认「歌单」「磁带」两个 chip 完整显示；档案页确认可见滚动条且能滑到第 12 个头像。

### C 组 艺术头像没有对齐大小（P1）

**现象**

### P2（低危 / 体验瑕疵，择机排入）

- `totalSecondsMs` 已在 releaseMediaPlayer 清零（本轮顺手修复），但 `playRunnable` 在页面最小化期间仍每 500ms 空转刷新不可见 UI，纯耗电小问题；
